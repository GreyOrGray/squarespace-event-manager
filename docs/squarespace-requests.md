# What the editor sends to Squarespace

Findings from a network recording of creating, editing and deleting one test event on 2026-10-30. The recording itself stays out of git. No cookies or tokens are copied here.

All requests go to the site's own editor domain (`https://<site>.squarespace.com`). That's the page the extension runs on, so the browser attaches the login cookies automatically.

## Authentication

Every write request carries an `x-csrf-token` header as well as the login cookies. Squarespace normally stores this value in a cookie named `crumb`, and the header repeats it. The extension needs to read `crumb` from `document.cookie` and send it as `x-csrf-token`. **To confirm in milestone 4:** the recording was sanitized, so the cookie itself isn't in it.

## Requests

| Step | Request | Notes |
|---|---|---|
| Create | `POST /api/content/calendars/{collectionId}/events` | JSON body. Sent with `x-autosave: true`. Returns the new item, including its `id`. |
| Update | `PUT /api/content/calendars/{collectionId}/events/{id}` | JSON body with the **whole** item, not just changed fields. The editor sent three of these as fields were filled in. |
| Delete | `DELETE /api/content-items/{id}` | No body. |
| Read one | `GET /api/content/calendars/{collectionId}/events/{id}` | Same shape as the update body. |
| List existing | `GET /api/content-collections/{collectionId}/content-items?limit=20` | Paged with a `start` cursor. Useful for the duplicate check. |

The Events page's `collectionId` is in the editor's address: `/config/pages/{collectionId}`.

**Don't send** `PUT /api/page-sections/...`. The editor sends it on every save, but it rewrites the whole Events **page** layout (header text, events list settings), not the event. The importer has no reason to touch it, and getting it wrong would break the Events page.

## The item body

These are the fields that matter. Everything else can be copied from the create response.

```json
{
  "title": "Summer Camp: Watercolor",
  "urlId": "summer-camp-2027-watercolor",
  "workflowState": 4,
  "structuredContent": {
    "_type": "CalendarEvent",
    "startDate": 1785166200000,
    "endDate": 1785529800000
  },
  "excerpt": { "html": "<p ...>...</p>", "raw": false },
  "body": { "raw": false, "layout": { "columns": 12, "rows": [ ... ] } },
  "location": { "addressTitle": "...", "addressLine1": "...", "addressLine2": "...",
                "addressCountry": "...", "mapLat": 0, "mapLng": 0, "mapZoom": 12,
                "markerLat": 0, "markerLng": 0 },
  "tags": [],
  "categories": []
}
```

- **`workflowState`:** `4` is draft, `1` is published. New events start as drafts.
- **Dates:** `structuredContent.startDate` and `endDate` are what count, in milliseconds since 1970 UTC. In one update the top-level `startDate` was stale while `structuredContent` held the new dates, and the server used `structuredContent`.
- **`urlId`:** the editor creates a random slug. When the title was first saved, the server replaced it with one made from the title (`test-1`). The importer should send its own slug, such as `summer-camp-2027-watercolor`.
- **`location`:** the create request was pre-filled with the site's default location. That default isn't in any response the importer can read, so the importer copies the location from the most recently added event instead, and the panel shows which one.
- **`excerpt`:** plain rich-text HTML.

## Body layout

The body is a 12-column layout: `rows`, each with `columns`, each with `blocks`. A text block looks like this, with long style objects shortened:

```json
{
  "type": 1337,
  "id": "2ca8b891a6d9b8c6fc67",
  "definitionName": "website.components.html",
  "value": {
    "engine": "wysiwyg",
    "html": "<p style=\"white-space:pre-wrap;\" data-rte-preserve-empty=\"true\">test</p><h2 ...>test</h2>",
    "source": "(same as html)",
    "containerStyles": { "...": "padding, borders, background" },
    "transforms": { "...": "offset, scale, rotation" },
    "animations": [], "breakpointOverrides": {}, "textAttributes": []
  }
}
```

The `layout` object also carried `legacyPromotedLayout: true`, `promotedBlockId: null`, `collectionId: null`, `parentItemId: <item id>` and `span: 12`. Block `id`s are 20 hex characters, generated by the editor.

## Featured image

Findings from a second recording that added images. The featured image uses one same-origin upload that attaches the image straight to the event.

1. `POST /api/commondata/SaveMedia` as `multipart/form-data` with these fields:

   | Field | Value |
   |---|---|
   | `process` | `true` |
   | `contentType` | the image's type, such as `image/png` |
   | `isWordpressXmlFile` | `false` |
   | `recordType` | `2` |
   | `collectionId` | the Events collection id |
   | `replaceItemId` | the **event's** id |
   | `imageDestination` | `content-item-main-image` |
   | `fileName` | file name |
   | `fileSize` | size in bytes |
   | `Filedata` | the file itself |

   The response holds the updated event and a `job` with an `id`.
2. Poll `GET /api/rest/jobs?id={job id}` until `status` is `3`. That took about 3 seconds. The finished job's `data.assetUrl` is the image address.

Later `PUT`s of the event that send `systemDataId: null` don't remove the featured image. The server keeps it.

## Body image

The body image goes through Squarespace's separate media service. That service allows requests from the site's editor domain with credentials. Because it's a different host, the extension must run on the `*.squarespace.com` editor address, not on a custom domain, so the media service's cookie counts as same-site.

1. `GET /api/media/auth/v1/library/authorization` returns `{"token": "..."}`. The token is short-lived.
2. `POST https://media-api.squarespace.com/user/authorize` with the token as a `text/plain` body and credentials included. Returns 204 and sets the media service's cookie.
3. `POST https://media-api.squarespace.com/uploads/image` as `multipart/form-data` with one field, `image`, holding the file. Send the headers `x-library-id: {websiteId}` and `x-sqsp-source: web upload`. Returns 202 with `jobId` and `checkStatusAfterMs`.
4. Poll `GET https://media-api.squarespace.com/jobs/image/status?job-list={jobId}` until `isSuccess` is true. Take the `assetId` from the result. Send this one **without credentials**: its reply allows the site's origin but not credentials, so with cookies Chrome blocks it. (Found in the first live test.)
5. `POST /api/uploads/images/asset-reference` with the form fields `assetId`, `libraryId={websiteId}` and `recordType=2`. The response's `media[0].id` is the image item's id. That id goes in the image block.
6. Optional: the editor then sent `POST /api/commondata/SaveItemField` twice, setting `filename` and `altText` on the image item.

`websiteId` is in every event's JSON.

## Image block with caption

The editor now creates image blocks as type `1337` with `definitionName: "website.components.imageLayout"`. Older events, including the 2026 camps, store the same settings as legacy type `5`. The `value` has the same fields either way. The important ones are:

```json
{
  "imageId": "<image item id from asset-reference>",
  "layout": "caption-below",
  "designLayout": "inline",
  "description": { "engine": "wysiwyg", "source": "", "html": "<h3>...</h3><p>...</p>" },
  "title": null,
  "subtitle": null,
  "imageLink": "none",
  "lightbox": false,
  "stretch": false
}
```

- **The caption is `description.html`.** That's where all the camp text goes.
- **`layout`** must be `caption-below` for the caption to show. The test block used `caption-hidden`.
- The 2026 camp's block also carries unused placeholder `title` and `subtitle` text ("Make it stand out"), which is hidden by its layout. The importer leaves them empty.
- The full stored camp event is in `test/fixtures/example-event.editor.json`.

## Updating an existing event

The importer updates an event by fetching the whole item with `GET /api/content/calendars/{collectionId}/events/{id}`, changing only the fields that differ, and sending it back with `PUT` to the same address. That's the same request the editor uses to save. Fields it doesn't change, including `workflowState`, the featured image and any image blocks, go back unchanged.

To replace the text, it edits the `html` and `source` of the body's only `website.components.html` block. If there are none, as in the 2026 events whose text is an image caption, or more than one, it refuses and asks for the text to be edited by hand.

## Changing an event's status

The status is the item's `workflowState`. The editor's code numbers them: 1 published, 2 scheduled, 3 needs review, 4 draft (5 private and 6 deleted aren't offered for events).

The editor's status picker changes the item and saves it with the same `PUT` as any other save. Its rule for the publish date, which the importer copies: switching to draft removes `publishOn`; switching to anything else keeps `publishOn`, or sets it to the current minute if there is none. Scheduling needs a date, so the importer leaves it to the editor.

## Replacing an event's flyer

The events list gives each event's featured image as `assetUrl`, ending in the uploaded file's name with spaces saved as `+`, for example `.../Watercolor.png`. An event without one has `hasFileData: false` and an address ending in a slash. The importer compares that name with the Image column, ignoring case, spaces and punctuation.

To replace the flyer it uploads the new image as for a new event, then saves the event with the image swapped into its only image block. Older events keep their text in that block's caption; the caption stays, since only `imageId` and `altText` change. With no image block, one is added above the text. With more than one, the update is refused before anything is uploaded. The featured image is then replaced with `SaveMedia`, as when creating. The old image stays in the asset library.
